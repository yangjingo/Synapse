# 技术博客成文

## 一条论证主线

文章和章节标题默认陈述证据能支持的技术判断。用户指定文章标题时，沿用原题。

1. 明确读者现在怎样判断、现实中哪一处和预期不符、为什么值得追查。用一个技术问题界定全文范围。
2. 给出有条件的当前结论。摘要优先用 2–3 句或 3–5 个短要点，覆盖答案、关键约束与证据边界。
3. 把每节组织成一个能改变判断的步骤。先确定本节问题，用首段交代读者已有的场景和遇到的卡点，接着给出判断，再展开论证。每个后续段落推进一个论证步骤。每 100–300 个中文字符检查是否有实质增量，节奏由内容决定。
4. 用一个实际请求或数据走完机制。依次说清谁产生数据，谁接收，状态在哪里存取，何时更新、可见、失效或被复用，最后怎样进入算子或输出。标识符、代码路径、版本和源码链接紧跟关键说法。
5. 结尾说明这个模型能解释什么、在哪些条件下需要改判。性能用可复现的环境、负载、基线、指标与边界来读，公开数字与自行实测清楚归因。

## 研究与编辑

- 从 vLLM、SGLang 等工程博客借鉴信息顺序。先交代场景与痛点，再放机制图和实验设置。按指标、基线和证据解释图表。使用自己的语言。
- 修订作者草稿时，保留第一人称判断、实际遇到的阻碍和原有语气。例如「我先试了把并发降到 1」交代了谁做了什么。只润色用户已经提供的经历。
- 材料分散时，可先用苏格拉底式追问整理概念依赖和证据缺口。给每个问题一个证据支持的参考回答，再决定哪些进入正文。草稿清楚区分第一手证据、来源说法和作者连接。
- 写作和终校时，逐句核对主语、动作、引用归因和术语。
- 多份参考稿或图表同时出现时，先统一名词、测量口径和适用范围。一段先给读者刚好够用的背景，随后用一句可复述的判断推进。避免重复小结、作者框架标签和营销腔。
- 完整论证可以写成短文或深度长文。用读者需要的上下文、例子、图表和源码阅读量来定长度。阶段性研究笔记用 `synapse-life-note`。

## 技术影响力

动笔前明确谁会用这篇文章、他们正在做什么判断，以及文中哪项证据会影响决定。给读者留一个能借用的机制模型、可核查的证据或复现实验，让结论在具体场景里派得上用场。已有读者反馈时，区分引用、复现、工程采纳和纠错。

## 成品与校验

- Markdown 成稿包含正文、图和来源。若同时交付 HTML 或另一语言版本，沿用同一份定稿，核对术语、数字、图序、图注、alt 和证据边界。原论文题名保留原文。
- 重排旧稿先保留原稿，再比对章节、图、表和源链接。遵循工作区已有的草稿与归档约定。交付 HTML 时核对桌面、窄屏和用户要求的离线行为。
- 内容与证据核验先于视觉整理。成稿展示读者需要的图、图注和链接。图像生成提示词留在工作材料里，按用户要求单独提供。
