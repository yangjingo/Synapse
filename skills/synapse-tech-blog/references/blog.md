# 技术长文与研究笔记

## 一条论证主线

标题优先陈述证据能支持的技术判断或张力。用户给定标题时保留原题。

1. 明确读者现在怎样判断、现实中哪一处和预期不符、为什么值得追查。用一个技术问题界定全文范围。
2. 给出有条件的当前结论。摘要优先用 2–3 句或 3–5 个短要点，覆盖答案、关键约束与证据边界。
3. 把每节组织成一个能改变判断的步骤。需要更多背景时，先交代对象、场景和失败条件，再给判断及因果解释。每 100–300 个中文字符检查是否有实质增量，节奏由内容决定。
4. 用一个实际请求或数据走完机制。依次说清谁产生数据，谁接收，状态在哪里存取，何时更新、可见、失效或被复用，最后怎样进入算子或输出。标识符、代码路径、版本和源码链接紧跟关键说法。
5. 结尾说明这个模型能解释什么、在哪些条件下需要改判。性能用可复现的环境、负载、基线、指标与边界来读，公开数字与自行实测清楚归因。

## 研究与编辑

- 从 vLLM、SGLang 等工程博客借鉴信息顺序。先交代场景与痛点，再放机制图和实验设置。按指标、基线和证据解释图表。使用自己的语言。
- 材料分散时，可先用苏格拉底式追问整理概念依赖和证据缺口。给每个问题一个证据支持的参考回答，再决定哪些进入正文。草稿清楚区分第一手证据、来源说法和作者连接。
- 正文引用用精确的短名直链到原论文、官方文档或固定提交。文末按需提供完整书目。未读或不可访问的链接记在工作笔记里，待补证据明确标注。
- 多份参考稿或图表同时出现时，先统一名词、测量口径和适用范围。一段先给读者刚好够用的背景，随后用一句可复述的判断推进。避免重复小结、作者框架标签和营销腔。
- 约 10 分钟的研究笔记通常选一个工程矛盾和 1–3 个相连问题，正文可参考 1,800–2,800 个中文字符。把相邻内容放入延伸阅读。约 30 分钟这样的阅读目标由示例、图表和源码阅读共同决定。

## 成品与校验

- 正常 Markdown 可含正文、图和参考来源。若同时交付 HTML，从同一份定稿生成，保持图序、数值和证据边界对应。
- 自包含阅读页使用 [工程博客模板](../assets/blog-template.html)。用 `python scripts/apply_template.py <existing.html>` 套用排版时，先保留原稿，再比对章节、图、表和源链接。脚本需要 `beautifulsoup4`。遵循工作区已有的草稿与归档约定。
- 请求 Synapse 版式或需要几何敏感排版时，用 `synapse-pretext` 的文章模板与渲染检查。用实际浏览器检查桌面和窄屏，验证目录、图、脚本和横向溢出。承诺离线时测试断网打开。
- 内容与证据核验先于视觉整理。发布稿展示读者需要的图、图注和链接。图像生成提示词留在工作材料里，按用户要求单独提供。
