# 技术博客成文

## 一条论证主线

标题优先陈述证据能支持的技术判断或张力。用户给定标题时保留原题。

1. 明确读者现在怎样判断、现实中哪一处和预期不符、为什么值得追查。用一个技术问题界定全文范围。
2. 给出有条件的当前结论。摘要优先用 2–3 句或 3–5 个短要点，覆盖答案、关键约束与证据边界。
3. 把每节组织成一个能改变判断的步骤。需要更多背景时，先交代对象、场景和失败条件，再给判断及因果解释。每 100–300 个中文字符检查是否有实质增量，节奏由内容决定。
4. 用一个实际请求或数据走完机制。依次说清谁产生数据，谁接收，状态在哪里存取，何时更新、可见、失效或被复用，最后怎样进入算子或输出。标识符、代码路径、版本和源码链接紧跟关键说法。
5. 结尾说明这个模型能解释什么、在哪些条件下需要改判。性能用可复现的环境、负载、基线、指标与边界来读，公开数字与自行实测清楚归因。

## 研究与编辑

- 从 vLLM、SGLang 等工程博客借鉴信息顺序。先交代场景与痛点，再放机制图和实验设置。按指标、基线和证据解释图表。使用自己的语言。
- 材料分散时，可先用苏格拉底式追问整理概念依赖和证据缺口。给每个问题一个证据支持的参考回答，再决定哪些进入正文。草稿清楚区分第一手证据、来源说法和作者连接。
- 正文引用用精确的短名直链到原论文、官方文档或固定提交。文末按需提供完整书目。未读或不可访问的链接记在工作笔记里，待补证据明确标注。
- 多份参考稿或图表同时出现时，先统一名词、测量口径和适用范围。一段先给读者刚好够用的背景，随后用一句可复述的判断推进。避免重复小结、作者框架标签和营销腔。
- 完整论证可以写成短文或深度长文。用读者需要的上下文、例子、图表和源码阅读量来定长度。阶段性研究笔记用 `synapse-life-note`。

## 技术影响力

动笔前明确谁会用这篇文章、他们正在做什么判断，以及文中哪项证据会影响决定。给读者留一个能借用的机制模型、可核查的证据或复现实验，让结论在具体场景里派得上用场。若已有发布反馈，区分引用、复现、工程采纳和纠错等实际信号。

## 复审句子与归因

1. **沿着动作找主体。** 检查摘要、各节首段、机制转折和图注。读者应能分清哪个组件读写状态、谁执行实验、谁提出解释。主体切换时写出名称。连续步骤已有清楚的共同主体时保持自然省略。

   例如，把「第二个请求到来时，找到已有 KV，再恢复状态」改成「第二个请求到来后，缓存管理器查找已有的 KV 并确认恢复位置。推理引擎从该位置继续处理请求。」主体应以具体实现为准。

2. **沿着判断找依据。** 用来源直接引出报告的结果，用前面的观测和成立条件引出推断。缺少实测时，把仍需验证的条件写明。段首直接陈述判断，移除给作者观点、推断或注解单独加的署名标签。

   例如，「报告只给出了单并发下的首 token 时延。如果高并发增加了复制和同步开销，缓存带来的收益可能缩小。研究团队还需保持请求分布和其他设置一致，只改变并发度来检验这一判断。」

3. **术语采用业内写法。** 中文稿沿用同行常用的英文、缩写或成熟中文术语，例如 `logits`、`LM head`、`KV Cache`、前向计算、交叉熵。第一次出现读者可能不熟悉的术语时，用一句短注交代它指什么或在当前流程里做什么。例如，「LM head 把每个位置的 hidden state 投影成整个词表的 logits。」后文和配图保持同一写法。

## 成品与校验

- 正常 Markdown 可含正文、图和参考来源。若同时交付 HTML，从同一份定稿生成，保持图序、数值和证据边界对应。
- 交付阅读页时参照 [HTML 排版](html-layout.md)中的中英文示例。重排旧稿先保留原稿，再比对章节、图、表和源链接。遵循工作区已有的草稿与归档约定。
- 请求 Synapse 版式或需要自适应排版时，读 [HTML 排版](html-layout.md)，核对桌面、窄屏和用户要求的离线行为。
- 内容与证据核验先于视觉整理。发布稿展示读者需要的图、图注和链接。图像生成提示词留在工作材料里，按用户要求单独提供。
