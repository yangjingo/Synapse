# Tech Blog · 技术博客

## 写给谁

写给正在理解系统或做工程选择的同行。技术影响力来自读者能验证你的判断，并知道什么时候能用到自己的项目里。

## 怎么写

1. **交代问题。** 写清读者面对的场景、目标、约束和预期落空的地方。篇幅有限时优先保住问题与背景，实现细节按论证所需取舍。
2. **先给判断。** 在引言用几句交代全文答案和适用条件。每个承担判断的小节先补够背景，再给结论，然后展开机制、证据与实现。用同一个具体例子贯穿前后，读者每次回到它能回答一个新问题。
3. **给出验证。** 写清关键动作由谁完成、依赖什么、怎样知道成功。主张尽量就近连到一手来源。性能结果交代负载、环境、指标和基线。结尾回到开篇的决定，让读者知道怎样在自己的系统中验证。

## 交付前核对

- 回读摘要、正文和图注。关键句尽早交代主体和动作，主体切换时写出组件或团队名。用来源、推导与适用条件标明判断的依据，移除作者名或品牌名式的观点标签。细则见[句子与归因复审](references/blog.md#复审句子与归因)。
- 作者经历和引语可追溯。各版共用审定稿，核对术语、数字、图序和来源。纯格式转换沿用审定稿的表达。
- 同一次线上故障，问「哪条机制推高了尾延迟，同行怎样复现」用本入口。要记录当时为何误判或自己学到了什么时，用 `synapse-life-note`。
